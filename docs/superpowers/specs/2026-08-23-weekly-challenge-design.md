# Weekly Challenge — Design Spec

## Why

SolPrep has ~238 signed-up parents (roughly ~476 children), but real usage
concentrates in a ~3 month window before SOL testing (Feb–Apr). Outside that
window the site is largely idle, so families forget it exists and have to be
"re-discovered" every spring.

Goal: **re-engage existing families year-round**, not drive new signups. New
signups are expected to come from word of mouth once retention improves —
this feature is not a growth/virality mechanic.

An earlier version of this idea included a public, speed-ranked leaderboard.
That was deliberately dropped:

- Public leaderboards need a critical mass of weekly solvers to not look
  dead; at current scale (238 families) that's a real risk, not a
  hypothetical one.
- SolPrep's own marketing (`blog/your-childs-privacy-on-solprep`) sells "no
  ads, no data selling, COPPA-compliant" as a trust differentiator. A public
  surface showing information about a specific child — even pseudonymously —
  cuts against that positioning for a feature whose actual goal is private
  retention, not public competition.
- Pure speed-ranking also invites parents/older siblings solving on the
  child's behalf, and demotivates anyone who isn't fastest.

## What we're building

A **weekly puzzle**, one per grade band (Elementary 3–5, Middle 6–8),
released every Monday. A family sees one puzzle per band that has a child in
it — two elementary children in one family share a single puzzle/attempt/
streak, they don't each get their own. No public leaderboard. A Monday email
reminds parents it's live and mentions their current streak.

### Puzzle formats (one fixed format per band, not a new format weekly)

- **Elementary (3–5): "Mystery Code."** 3 short math/reading questions; each
  correct answer reveals one digit/letter of a hidden code. Solving the full
  code is the win condition. Visual, low reading burden.
- **Middle (6–8): "SOLdle."** A Wordle-style deduction puzzle built around a
  math/science concept (ratios, percents, coordinate-plane style clues).
  Familiar mechanic for this age group, fits a more analytical/peer-status
  motivation.

Both share one underlying shape: a puzzle has `content` (what's shown) and a
`solution` (what's checked against), with one submit/attempt flow per format.

### Content generation — offline, zero runtime AI cost

Per existing project preference, puzzles are **not** generated by a live API
call in the app. They're authored in batches via a Claude Code terminal
session (the same pattern as `scripts/generate-grade5-science.ts`), written
into the database as `pending`, then reviewed and approved by the site owner
before they can ever be released — mirroring the existing
`questions_pending` → `questions` approve workflow
(`supabase/migrations/0011_questions_pending.sql`).

Release is just "pick the earliest unreleased `approved` row for this band"
— no generation happens at release time.

**First batch for review: 4 weeks each of Mystery Code and SOLdle** (8
puzzles total), generated and left in `pending` status for manual review
before anything is wired up to release automatically.

## Data model

```sql
CREATE TABLE weekly_puzzles (
  id uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  band text NOT NULL CHECK (band IN ('elementary', 'middle')),
  puzzle_type text NOT NULL CHECK (puzzle_type IN ('mystery_code', 'soldle')),
  week_start_date date,               -- NULL until scheduled; set on approval/scheduling
  title text NOT NULL,
  content jsonb NOT NULL,             -- clues / grid data, shape depends on puzzle_type
  solution jsonb NOT NULL,            -- answer-checking data, shape depends on puzzle_type
  status text NOT NULL DEFAULT 'pending' CHECK (status IN ('pending', 'approved', 'rejected')),
  generated_at timestamptz NOT NULL DEFAULT now(),
  reviewed_at timestamptz,
  reviewed_by uuid REFERENCES parents(id),
  CONSTRAINT review_columns_consistent CHECK (
    (reviewed_at IS NULL AND reviewed_by IS NULL) OR
    (reviewed_at IS NOT NULL AND reviewed_by IS NOT NULL)
  )
);
-- Enforced once a week_start_date is assigned (partial unique index):
CREATE UNIQUE INDEX idx_weekly_puzzles_band_week
  ON weekly_puzzles(band, week_start_date) WHERE week_start_date IS NOT NULL;

ALTER TABLE weekly_puzzles ENABLE ROW LEVEL SECURITY;
CREATE POLICY "weekly_puzzles_admin_write" ON weekly_puzzles
  FOR ALL USING (EXISTS (SELECT 1 FROM parents WHERE id = auth.uid() AND is_admin = true));
CREATE POLICY "weekly_puzzles_approved_read" ON weekly_puzzles
  FOR SELECT USING (status = 'approved');


CREATE TABLE weekly_puzzle_attempts (
  id uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  parent_id uuid NOT NULL REFERENCES parents(id) ON DELETE CASCADE,
  puzzle_id uuid NOT NULL REFERENCES weekly_puzzles(id) ON DELETE CASCADE,
  band text NOT NULL CHECK (band IN ('elementary', 'middle')),
  solved_at timestamptz,
  attempt_count int NOT NULL DEFAULT 0,
  created_at timestamptz NOT NULL DEFAULT now(),
  UNIQUE(parent_id, puzzle_id)
);
ALTER TABLE weekly_puzzle_attempts ENABLE ROW LEVEL SECURITY;
CREATE POLICY "weekly_puzzle_attempts_own" ON weekly_puzzle_attempts
  FOR ALL USING (parent_id = auth.uid());


ALTER TABLE parents
  ADD COLUMN IF NOT EXISTS current_streak_elementary int NOT NULL DEFAULT 0,
  ADD COLUMN IF NOT EXISTS best_streak_elementary    int NOT NULL DEFAULT 0,
  ADD COLUMN IF NOT EXISTS last_solved_week_elementary date,
  ADD COLUMN IF NOT EXISTS current_streak_middle      int NOT NULL DEFAULT 0,
  ADD COLUMN IF NOT EXISTS best_streak_middle         int NOT NULL DEFAULT 0,
  ADD COLUMN IF NOT EXISTS last_solved_week_middle    date;
```

Streak update rule (applied on solve, per band): if
`last_solved_week_<band>` is exactly 7 days before the puzzle's
`week_start_date`, increment `current_streak_<band>`; otherwise reset it to
1. Always update `best_streak_<band>` to the max, and set
`last_solved_week_<band>` to this puzzle's `week_start_date`.

A family only has a puzzle/streak for a band if they have at least one
child in that grade range — a family with only elementary children never
sees a Middle puzzle or accrues a `_middle` streak.

## Page & release flow

- New route (e.g. `/challenge`), reachable once logged in. For each band the
  family has a child in, resolve "this week's" puzzle: the `approved` row
  for that band with the current `week_start_date` (America/New_York week,
  Monday start).
- Rendering branches on `puzzle_type` — a `MysteryCode` component and a
  `Soldle` component, both taking `content` and reporting an answer back to
  a shared submit handler that checks against `solution`, writes/updates
  `weekly_puzzle_attempts`, and updates the parent's streak columns on
  first solve.
- No admin UI is being built as part of this pass — puzzle review/approval
  and week scheduling are done directly via Supabase, matching how
  `questions_pending` is reviewed today (per `scripts/approve-*.ts`
  patterns).

## Email

- Monday morning, Resend send via `lib/email/resend.ts` to every parent
  with at least one child, using a plain-text-first template consistent
  with existing transactional emails: "This week's challenge is live" +
  link to `/challenge`, and if `current_streak_<band> > 0` for a relevant
  band, a line mentioning the streak.
- No mid-week reminder in this pass.

## Explicitly out of scope for this pass

- Public/shared leaderboard of any kind.
- District/school/county tagging.
- Per-child (rather than per-family-band) puzzles or streaks.
- Live/runtime AI generation of puzzles.
- Automated weekly content generation — puzzles are authored in manual
  batches via Claude Code sessions.
- Mid-week reminder emails.
- Admin review UI — review happens via direct DB access, as with existing
  pending-content workflows.

## Testing

- Puzzle answer-checking logic (`MysteryCode`/`Soldle` solution matching)
  is pure and unit-testable independent of the DB/UI.
- Streak-update logic (the 7-day-consecutive rule) is a pure function of
  `(last_solved_week, new_week_start_date)` → `(new_streak)` and should be
  unit tested directly, including the reset and first-ever-solve cases.
- RLS policies verified the same way existing per-parent tables are
  (`weekly_puzzle_attempts_own` mirrors `sessions_by_parent`).
